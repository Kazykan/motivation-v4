# Контекст и архитектурные правила проекта (AI Guidelines)

## 1. Общие принципы

- Проект разделен на две изолированные роли: **Parent (Родитель)** и **Child (Ребенок)**.
- Строго запрещено смешивать бизнес-логику, компоненты и API-вызовы разных ролей в общих файлах. Каждая роль имеет собственную структуру в `src/app/parent/` и `src/app/child/`.
- Все переменные окружения должны браться исключительно из `.env` файлов (например, `process.env.NEXT_PUBLIC_API_URL`). Хардкод URL и ключей строго запрещен.

## 2. Архитектура и State Management (Zustand)

- Для отложенной отправки данных и индикации используется Zustand.
- Хранилище должно содержать:
  1. Буфер изменений.
  2. Флаг синхронизации (`isSyncing: boolean`).
  3. Идентификатор таймера для дебаунса.
- **Optimistic Updates:** Состояние интерфейса обновляется мгновенно. Предыдущий таймер сбрасывается, запускается новый таймер на 1 секунду (дебаунс), после чего буфер отправляется на бэкенд через Axios, а флаг `isSyncing` переводится в `true`.

## 3. API и Сервисы

- Запросы к бэкенду разделены на `parentApi.ts` и `childApi.ts`.
- Используется единый экземпляр Axios (`src/lib/axios.ts`), сконфигурированный через переменные окружения.

## 4. Стиль кода и требования

- Никаких лишних комментариев, эмодзи, «воды» или софт-тока при генерации кода. Только строгая техническая реализация.
- Использовать TypeScript, Tailwind CSS и компоненты интерфейса согласно дизайн-системе. Приоритет отдается компонентам shadcn/ui. Кастомные компоненты создаются только при отсутствии подходящих аналогов в shadcn/ui.
- цвета брать только из global.css
- Дробить интерфейсные элементы на модульные переиспользуемые компоненты для исключения дублирования кода и поддержания единого стиля дизайна. Проверять на дублирование компонентов предлагать бути решения.
- Все функции должны быть отдельно если они будут переиспользоваться не в файлах page.tsx
- Все пропсы должны быть в отдельном файле

## 5. Кеширование, Optimistic Updates и фоновая синхронизация (TanStack Query)

- Все изменения данных в интерфейсе (особенно частые клики, переключения статусов, календари) должны использовать **Optimistic Updates** (мгновенное локальное обновление стейта / кэша TanStack Query через `queryClient.setQueryData`).
- Сетевые запросы на модификацию данных должны выполняться с использованием **дебаунса (debounce)** и буферизации (например, через Zustand-хранилища вроде `useLogSyncStore`), чтобы объединять быстрые клики пользователя в пакетные запросы.
- Пользователь должен видеть визуальный индикатор фонового сохранения (статус синхронизации `isSyncing`), когда данные отправляются на бэкенд.
- По завершении фоновых запросов обязательно производить инвалидацию соответствующих ключей кеша (`queryClient.invalidateQueries`) для поддержания актуальности данных.


## Правила работы с API (BFF Pattern)
1. Клиентский код отправляет запросы только на локальные маршруты Next.js (`/api/...`).
2. Внешний Django-бэкенд недоступен напрямую из браузера; запросы к нему осуществляются через Next.js Route Handlers.
3. Передача секретных заголовков (Telegram ID, токены авторизации) выполняется на стороне сервера Next.js.


# Концепция приложения

## Модель

**Родитель = работодатель, ребёнок = работник.** Родитель устанавливает цену за работу, ребёнок сам решает, выполнять её или нет. Никаких нотаций и принуждения — только цена и факт.

## Экономика задания

- Задание имеет **недельную цену** (`weekly_price`) и правило выполнения:
  - **FLEXIBLE** — N выполнений за неделю (например, «2 пятёрки по английскому = 500 ₽, по 250 ₽ за раз»).
  - **FIXED** — конкретные дни недели (например, «уборка 5 из 5 = 50 ₽, по 10 ₽ за раз»).
- Приоритет родителя выражается **ценой**: важное стоит дороже. Иерархия «английский 500 > танцы 100 > уборка 50» — это и есть приоритеты, без текстовых нотаций.
- Цена за одно выполнение = `weekly_price / число выполнений` (с распределением копеек).

## Цикл использования

Приложение **недельное**, не дневное. Реальный паттерн: ребёнок заходит в конце недели и отмечает дни, родитель раз в неделю проверяет и платит. **Не проектировать под ежедневный заход, не добавлять ежедневную геймификацию, не делать кнопку «заходи каждый день».**

## Ключевой принцип: честность через трение

- **Один клик = один день = одна отметка.** Нельзя «отметить всё» одной кнопкой — это легализация обмана и убивает доверие родителя к данным.
- **Нельзя отмечать будущие дни.** Прошлые — можно (ребёнок в воскресенье отмечает понедельник).
- **Родитель подтверждает поштучно**, без bulk-approve в UI. Трение = честность с обеих сторон.
- Трение — фича, а не баг. Оно отделяет «я реально сделал» от «я хочу денег».

## Три вкладки ребёнка

| Вкладка | Вопрос ребёнка | Содержимое |
|---|---|---|
| **Задания** | «Что мне сделать?» | Сетка «задание × 7 дней», отметка кликом по ячейке, деньги по каждому клику сразу. Без CTA «отметить сегодня/всё». |
| **Кошелёк** | «Сколько у меня денег?» | Всего накоплено, эта неделя (заработано / ждёт проверки / можно ещё), история выплат со статусом. |
| **Профиль** | «Кто я?» | Имя, возраст, семья, успехи (всего выполнено, лучшая неделя). Без технотекста и «обновить сессию». |

## Что запрещено

- Кнопка «отметить всё» / «отправить неделю» у ребёнка.
- Bulk-approve в UI родителя.
- Ежедневная геймификация, стрики, «зайди каждый день».
- Блок «Сегодня» с отдельными CTA.
- Хардкод сумм и заглушки в данных (например, `earned || 300`).
- Финансовые термины для взрослых («Максимум», «Итого», «Прогноз») — использовать детские формулировки («Можно заработать», «Ждёт проверки родителя»).

## Деньги в UI

- Сумма за одно выполнение видна **в карточке задания** (`+250 ₽ за раз`).
- После каждого клика — **немедленная обратная связь**: `+250 ₽ ждёт проверки`.
- Сверху недели: `Заработано · Ждёт проверки · Можно ещё` — не «Максимум/Итого».

## Будущее (не сейчас)

- Настройка вида: недельный / дневной режим.
- Цель накопления («коплю на наушники») с прогресс-баром.
